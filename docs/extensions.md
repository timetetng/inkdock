# InkDock 服务扩展架构草案

更新：2026-10-18
状态：需求已确认；以下技术机制为拟议方案，尚未实现或验证。本文覆盖 P0 工作单中原先“不做插件系统”的约束。

## 1. 目标与边界

InkDock 只服务行简本机，不追求通用管理软件；但容器内服务持续增加，因此新增服务管理能力应尽量不修改宿主页面代码、不为每个服务新建 Android 模块。

需要支持类似插件的安装方式。先定义稳定扩展契约、宿主组件与服务适配边界，再逐步实现安装生命周期。不做插件市场、远程管理、任意 Android 代码热加载。

终端非硬需求，独立后置，不作为扩展接入前提。

## 2. 分层

Android 原生宿主（Compose）
→ 扩展注册表 / 页面渲染 / 操作与任务调度 / 权限与凭据接口
→ 类型化能力接口
→ 本地 root bridge
→ 服务适配器（Docker、systemd、mihomo、Pi 等）
→ 本机容器中的服务 API 或受控命令

- 页面不能直接读取服务内部存储或拼接 shell。
- 适配器屏蔽服务版本、文件格式及接口差异。
- 通用宿主负责导航、主题、加载/空态/错误、确认、任务、权限、缓存及审计。
- 不为扩展开放任意 root 命令接口，不暴露 Docker TCP 或无认证管理端口。

## 3. 两类扩展

### 3.1 声明式服务扩展（优先）

扩展包包含 manifest、页面描述及必要的静态资源；只引用宿主已注册的能力和适配器，不包含可直接执行的 shell、dex、动态库或 JS。

manifest 拟包含：id、名称、扩展版本、协议版本、宿主兼容范围、所需适配器版本、能力与权限、页面入口、配置 schema。最终字段及打包格式由后续 ADR 固定。

宿主组件：状态卡、分页/可搜索列表、详情、表单、模型选择器、日志流、进度、操作按钮、危险确认、凭据组件。

典型新服务若复用现有 HTTP/任务/配置能力，主要增加声明和适配配置，不新写 Android 页面。

限制：声明式不是万能低代码。遇到新协议、复杂数据处理或未知服务内部格式，仍需新增受审查的服务适配器；不能宣称所有未来服务只安装一个 JSON 就能管理。

### 3.2 原生功能（例外）

文件浏览、特殊图表等通用组件无法覆盖时，使用编译入 APK 的 Kotlin 功能。与声明式扩展共享能力接口和权限模型，避免两套管理逻辑。

独立 APK 插件、下载 dex、热加载 Compose 暂不实现；以后确有必要再评估 IPC、签名校验和兼容性。

## 4. 契约边界

拟定义以下语义接口，具体语言类型和 wire format 尚未冻结：

- Discovery：识别服务、报告可用能力与不可用原因。
- Query：分页、过滤、排序；稳定实体 ID；明确数据时间与来源。
- Action：类型化参数、操作风险级别、确认信息、幂等性声明与结构化结果。
- Task：任务 ID、状态、进度、日志/事件、取消能力、超时、结束原因。
- Event：有界缓冲、订阅释放、断线及重连语义；来源支持时才提供游标续传。
- Config：字段校验、敏感标记、版本冲突检查、变更预览；适配器声明是否可回滚、是否需重启。
- Credential：只返回是否配置及必要的脱敏信息，写入/替换/删除单独授权。

统一错误区分：未安装、容器停止、权限拒绝、能力不支持、超时、数据格式不兼容、服务故障。不能把失败显示成空列表。

取消只能承诺中止请求；不支持服务侧取消时必须说明，不伪装任务已经停止。失败操作不默认自动重试，尤其是非幂等写操作。

## 5. 权限与信任

- 读状态、读日志、读文件、写配置、管理凭据、启停、执行任务分别声明。
- 权限不仅在 UI 检查，也在 bridge/适配器执行边界检查。
- 宿主验证操作 ID、参数 schema、路径与资源范围；动态值通过安全参数传递，不拼 shell。
- 声明式包的安装不授予任意命令执行；未知能力拒绝加载。
- API key 不进入扩展包、仓库、日志、分析事件、导出诊断或普通配置返回值。
- 凭据存储按实际服务选择：必要时保留服务原有受限文件作为事实来源；Android 自有凭据使用 Keystore 支持的加密存储。禁止把已有 key 擅自复制多份。
- 替换 key 不回显完整明文；剪贴板复制不作为默认功能。
- 权限声明不是安全沙箱。若未来允许安装后端可执行适配器，必须作为高信任代码单独确认和审查，不能沿用“纯声明式包”的安全承诺。

## 6. 安装与生命周期（分期实现）

本地导入 → 校验路径/大小/格式/协议 → 展示来源、权限与变更 → 用户确认 → 原子注册 → 启用。

- 安装包不允许路径穿越、资源越界、无限深嵌套或解压膨胀；限额数值实现时确定。
- 扩展身份与版本稳定；同 ID 更新需要明确来源信任策略，不能仅凭文件名或哈希认定可信。
- 升级先校验配置迁移，失败保留旧版本；不默默迁移服务原配置。
- 支持禁用、卸载、失败恢复；卸载默认不删服务本身及业务数据。
- 扩展故障局部呈现，限流、超时和事件缓冲不能拖垮首页。
- 初期不实现远程下载和自动更新。签名或其他来源验证策略待 ADR 决策，未解决前只允许用户明确确认的本地导入，不宣称已提供供应链安全。

## 7. Pi：架构验收案例

目标能力：

| 场景 | 通用组件 | 适配器职责 |
| --- | --- | --- |
| 会话历史 | 分页列表、搜索、详情 | 会话格式版本、读取与消息脱敏 |
| subpi 进度 | 任务列表、事件流、取消操作 | 任务身份、真实进度、取消能力 |
| 模型管理 | 表单、选择器、校验 | 实际配置来源、模型字段与生效方式 |
| API key 管理 | 凭据组件、替换/删除确认 | 安全读写、权限、避免并发覆盖 |

Pi 当前是否具备稳定 API、事件协议和安全的配置写入方式尚未验证。不能把“后台日志尾部”直接冒充准确进度，也不能假定会话文件可在运行中随意修改。

只读历史与运行任务先做；模型与 key 写入需变更预览、冲突检查、生效方式说明，后做。

## 8. 阶段与验收

P0：将本文合并进 requirements / architecture / roadmap；明确接口草案和待决策，不实现完整插件引擎。

P1：在 Docker 真实闭环中保持 UI、能力接口、适配器分层；增加一个不接触隐私的声明式样例，只验证既有组件与受控能力组合，不扩张为插件平台。

扩展里程碑：完成本地导入/禁用/卸载、版本拒绝、未知能力拒绝、权限拒绝、恶意路径测试、局部故障和缓存清理测试。

Pi 里程碑：使用同一契约接入真实的只读会话/任务能力；不得复制整套页面；新协议只加适配器。写入模型与凭据作为独立验收项。

“无需修改宿主页面代码增加一种可由已有组件表达的服务”是架构验收标准，不是承诺任意服务零代码接入。

## 9. 尚待决策

- root bridge 的实现语言、生命周期及通信协议。
- 声明式 schema、表达能力上限和绑定规则；禁止任意代码求值。
- 适配器运行位置、发布与兼容机制。
- 本地扩展包格式、限额与来源验证。
- Pi 的实际数据源、版本兼容、任务事件与配置生效机制。

以上均需验证后形成 ADR，不把聊天中的建议写成已经实现的事实。
